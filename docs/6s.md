# Bench audits and process instructions

I wanted the measurements in DistroFit to have a repeatable path from a tidy,
ready bench to a reviewed analysis. I use this page to record what was actually
observed, keep the previous checks, and see which gaps keep returning.

## Try the complete example

Install the normal Python requirements and Graphviz, the program that lays out
the flow chart:

```sh
brew install graphviz
# Ubuntu or Debian: sudo apt-get install graphviz
python six_s_report.py --sample --out /tmp/distrofit-bench-review
open /tmp/distrofit-bench-review/index.html
```

On Linux, open that HTML file in a browser. The output folder must be new. It
contains the original audit history, score and finding tables, two chart images,
the process step list, Graphviz source, an SVG diagram and a standalone SOP page.
The SOP includes the diagram and works offline. I can print it from the browser.
The [committed diagram](../examples/lean/process.svg) and
[SOP page](../examples/lean/sop.html) come from the same example step list.

To use the app, run `python -m streamlit run DistroFit.py` and choose
**Workplace organization** in the sidebar. The three tabs let me record an audit,
review its history, and generate process instructions. The history tab opens
empty. **Use synthetic demo (replace session)** loads three generated audits;
**Start empty history (replace session)** clears them before recording my own.

## What I score

The checklist has two measurement-bench questions under each pillar:

| Pillar | What I look for |
| --- | --- |
| Sort | Only needed tools and samples remain; rejected items are separated |
| Set in order | Tools have labelled homes; incoming, accepted and held samples stay separate |
| Shine | Measuring surfaces are clean; damage or wear is recorded |
| Standardize | Current methods, limits, units and calibration records are available |
| Sustain | Scheduled checks and previous corrective actions have dated evidence |
| Safety | Access is clear; required guards, protection and handling instructions are available |

I adapted the six pillars described in the
[EPA Lean and Environment Toolkit](https://www.epa.gov/sustainability/lean-environment-toolkit-chapter-5).
The bench questions and scoring rubric are my project conventions, not an EPA
rating system or a safety certification. A local supervisor must adapt and approve
the checklist and procedure for the actual work. The checklist does not establish
regulatory compliance or cover every hazard.

| Score | Meaning against the posted local standard |
| --- | --- |
| 0 | Standard absent |
| 1 | Informal or rarely followed |
| 2 | Partly followed |
| 3 | Mostly met, with a remaining gap |
| 4 | Fully observed |
| N/A | Not applicable, with a written reason |

Every answer needs observed evidence, including a reason for N/A. Each score
below 4 is a finding and requires an action, responsible role and due date on or
after the audit date. The app starts every answer at **Not scored** so an
untouched checklist cannot become a perfect audit. I resolve unsafe conditions
through the local safety process regardless of the numeric score.

The score is `earned points / (4 × applicable checks) × 100`. N/A earns no points
and is excluded from the denominator. An all-N/A audit is rejected. A pillar with
only N/A checks has no score. For example, ten scores of 4, a safety score of 0
and one N/A give 40/44, or 90.91%, while Safety is 0%. The page keeps the safety
finding visible beside the total so the high overall number cannot hide it.

## History and finding counts

Each saved snapshot has a unique ID, area, date, reviewer or role, checklist
version and all 12 responses. Saving appends a validated copy; editing the draft
does not change the old snapshot. The same unchanged draft cannot be submitted
twice. History is in the Streamlit session, not a shared database. I download
**audit_history.json** before closing the page or restarting the app and restore
that backup next time. Restoring replaces the session only after every record
passes validation. There is no merge of competing backups or user authentication.

The portable format has `schema_version: 1` and an `audits` list. Each audit has
exactly `audit_id`, `area`, `date` (YYYY-MM-DD), `auditor`,
`checklist_version: 1` and `responses`. A response has `item_id`, integer `score`
(0–4, or JSON `null` for N/A), `evidence`, `action`, `owner` and `due`.
The [example history](../examples/lean/audit_history.json) is a complete template.
Import is limited to 2 MB and 1,000 audits; text fields are limited to 2,000
characters. Unknown versions, missing or duplicated checklist items, duplicate
audit IDs, invalid scores and incomplete actions are rejected.

I compare the same exact area name and checklist version, keeping the applicable
and N/A counts visible. More exclusions can increase a score without improving
the bench. The trend orders snapshots by date, preserving save order within the
same date (or list order when restoring a backup).
The example rises from 24/48 to 36/48 to 44/48 points, or 50%, 75% and 91.67%.
These are generated observations, not measured improvement in a real workplace.

The Pareto chart ranks finding observations by pillar. A gap repeated on three
audit dates counts three times. The example has 26 findings: Safety has six and
each other pillar has four. Bars count observations, not lost points or risk.
The cumulative line shows the share covered by the leading pillars. The finding
table preserves the question, evidence, action, role and due date for follow-up.
An action in an old audit remains historical; this is not an open-ticket register
and does not infer whether a previous action is overdue or closed.

I can recreate the report from a saved backup and an approved process:

```sh
python six_s_report.py --history audit_history.json \
  --process examples/lean/measurement_process.json --out /tmp/my-bench-review
```

Separate areas get separate trend and Pareto charts. The combined CSV files keep
their area column. An empty history produces empty tables and the process SOP.

## One source for the diagram and SOP

The process JSON contains `title`, `revision`, `purpose`, `start` and `steps`.
Each step has a unique `id`, a `kind` (`task`, `decision` or `end`), `title`,
`owner`, `instruction`, `record` and `next` routes. IDs start with a letter and
contain only letters, digits, underscores and hyphens. Each route has `to` (a
step ID) and `label`. Tasks have one route; decisions have two distinct,
nonblank labels and destinations; ends have none.

The example starts with receipt and bench preparation, checks calibration and
readiness, holds samples when needed, measures, reviews the log, resolves issues,
compares curves in DistroFit, and archives the reviewed result. Rework loops are
allowed. Validation rejects missing destinations, unreachable steps and steps
that cannot reach an end. That proves a route exists; it cannot guarantee that
real work eventually leaves a rework loop. Step order supplies reference numbers;
the labelled routes determine the actual work sequence.

`process_flow.py` converts this list to quoted Graphviz DOT text and runs
[`dot -Tsvg`](https://graphviz.org/doc/info/command.html) with a 20-second timeout.
Tasks are boxes, decisions diamonds and ends ovals. A Start arrow marks the
declared starting step, even when it is not first in the list. The same validated steps
produce an escaped HTML SOP with each role, instruction, record and linked next
step. User text cannot add graph attributes or executable HTML. Graphviz is a
system dependency; no extra Python graph package is needed. The app removes old
downloads immediately when the source changes or generation fails.

## Checks and boundaries

The tests use hand-calculated scores, invalid and missing answers, immutable
history, area isolation, repeat counts, real Graphviz SVG parsing, rework loops,
invalid graph routes, and HTML escaping. Command-line tests recreate a report
from its exported inputs and check that an existing folder is never overwritten.
Streamlit tests save an audit, reject incomplete actions without changing history,
restore a backup, and remove stale process downloads. CI installs Graphviz,
runs the full suite and publishes the generated example as an artifact.

Audit imports and generated reports may include entered evidence. I keep private
records out of GitHub and share only generated examples here. The browser page
has no account system, centralized storage, signed approvals or revision
authorization. The process is documented standard work for this example, not a
validated procedure for a regulated lab or a product-release decision.
